## 本轮确认的问题

### 1. P1：短屏长文章正文持续透明，滚动和目录跳转都不能恢复

位置：`src/layouts/PostLayout.astro:78`、`src/layouts/BaseLayout.astro:143`、`:159`、`src/styles/global.css:251`、`:560`。

复现页面：`/ios/2019/08/10/source-Aspects/`，视口 320×568。初始正文顶部约 630px，整段正文高约 29,261px；滚动到 250、500、750、1,500px 后，正文仍是 `opacity: 0`，没有 `is-visible`。点击移动目录跳到文章后部也相同。新构建的静态 HTML 与开发服务器均复现，因而不是开发缓存问题。

原因是整个长正文使用一个 `.reveal`，初始没有进入视口的内容交给 `threshold: 0.05` 的 IntersectionObserver。这个短屏可见区域约 523px，远小于整段正文高度的 5%。只在浏览器测试中把阈值改为 0 后，正文在第一次滚动时就恢复，随后 opacity 为 1。`prefers-reduced-motion` 下也仍为空白，因为 `.reveal` 的恢复规则优先级低于 `html.reveal-ready .reveal:not(.is-visible)`。

建议：文章正文默认可见，取消整篇正文的入场动画；其他元素若保留动画，应使用不会受整块高度限制的触发方式，并让减少动态效果的覆盖规则真正生效。

验收：320×568 与横屏短视口下，长文自然滚动、目录跳转、减少动态效果模式均能读到正文；同时检查初始不在视口内的其他长区块。

证据：[实际空白](audits/2026-09-06-round2/reveal-4323-wheel.png)、[仅修改浏览器阈值后的对照](audits/2026-09-06-round2/reveal-4323-threshold0.png)、[原始滚动记录](audits/2026-09-06-round2/reveal-4323-results.json)。对照仅用于确认原因，没有写入项目代码。

### 2. P2：32KB 请求体限制可被无 Content-Length 的请求绕过

位置：`src/pages/api/chat.ts:32`、`:46`、`:56`，`src/lib/chat-request.ts:84`。

实际本地 HTTP 测试使用 `Transfer-Encoding: chunked`，发送包含正常静态问题和一个大额外字段的 100,062 字节 JSON，接口仍返回 200。缺少 Content-Length 时，`Number('')` 得到 0，后续把它作为有效大小，跳过估算分支；而 `request.json()` 已经先完整读取和解析了请求。

估算分支自身还有两个问题：`JSON.stringify(...).length` 是 UTF-16 长度而非 UTF-8 字节数；重新组装对象后又忽略了未知字段。模块测试中，48,130 字节的多字节内容也能通过估算路径。

建议：对原始 body 流按实际字节计数，超过上限即停止读取并返回 413，然后再解析 JSON 和验证结构。不能只信任声明长度。补真实 Request/HTTP 级用例：缺少长度、多字节、额外字段和流式超限。

首轮的 `null`、`messages:[null]`、数字 content 导致 500 的问题已修复，这条发现针对新增大小限制的有效性，不是说运行时校验没有价值。本次没有对生产地址进行超大请求测试。

### 3. P2：旧错误消息上的“重试”会重发另一个问题，或点击无效

位置：`src/components/Chatbot.tsx:167`、`:258`、`:340`。

所有历史错误气泡都显示重试按钮，但回调读取同一个 `lastFailed.current`。浏览器中模拟两次 503，依次发送“苹果甲”“苹果乙”，点击第一条错误的重试，实际发送顺序是“甲、乙、乙”。之后成功回答一个静态问题会清空 `lastFailed`，前面的按钮仍保留，点击却不再发请求。

建议：把失败请求与消息 ID、问题和当时的上下文绑定；或者仅为最后一个可重试失败显示按钮。验收应包含连续失败、后续成功、点击旧错误三种情况。

### 4. P2：模型上游故障仍被当成正常静态回答

位置：`src/lib/llm.ts:95`、`src/pages/api/chat.ts:77`、`src/components/Chatbot.tsx:108`。

模块测试让模型调用抛出 `upstream timeout`，最终 API 返回 200、`source: static` 和普通“暂时答不上来”，连 error 字段也被二次静态兜底抹掉。新加入的客户端错误气泡和重试按钮处理了非 2xx，却没有覆盖这条实际服务端失败路径。

建议：区分“没有配置模型”和“已配置模型发生超时/故障”。前者可以正常静态兜底，后者保留可识别的错误状态，例如 502/504 或明确的结果类型，让客户端显示对应状态。失败时仍可提供有用文字，但不要丢失失败语义。

本项通过模拟上游验证，未消耗真实模型额度，也未认定线上模型此刻故障。

### 5. P2：长问题在发送时静默截断，用户看见的内容与服务端收到的不同

位置：`src/components/Chatbot.tsx:75`、`:193`、`:387`。

输入 4,000 个“汉”再加“请回答最后这句”，界面气泡保存 4,007 字符，实际请求只有前 4,000 字符，真正的问题被丢掉。输入控件没有对应长度限制或错误提示。

建议：最新用户消息超限时明确阻止发送并提示，或在输入阶段呈现一致的限制；只对旧历史做单独的上下文裁剪。不要让界面保留一份服务端从未收到的提问。

### 6. P2：等待异步回复时禁用输入框，回复后键盘焦点丢失

位置：`src/components/Chatbot.tsx:254`、`:394`。

键盘 Enter 提交一个需要 API 的问题后，输入框被 disabled；请求完成重新启用时，`document.activeElement` 是 BODY，继续打字不会进入输入框。静态即时回答不会走这个状态，因此普通演示容易漏掉。

建议：等待期间用合适的只读状态，或只在用户没有主动移动焦点时恢复输入焦点；防重复发送继续由 busy 控制。关闭聊天后的 Escape 焦点恢复这轮已经修好。

### 7. P2：联系回答中生成了错误的 X 链接

位置：`src/components/Chatbot.tsx:117`，`src/data/knowledge.ts:35`。

当前 URL 正则只在空白处停止，联系人回复里的中文括号被吞进地址，浏览器实际 href 为 `https://x.com/toolazytoname（不活跃，主互动在`。

### 11. P2：URL 校验的手写 YAML 解析与站点不一致，会拒绝合法文章

位置：`scripts/verify-urls.py:38`、`:59`；对照 `src/content.config.ts:26`、`src/lib/permalink.ts:30`。

合法 frontmatter `categories: [life, craft]` 被脚本当成字符串，得到 `life/craft/2026/09/06/test/`；Astro schema 接受数组，真实路由取第一个分类，得到 `life/2026/09/06/test/`。因此新增这种文章可以构建成功，却在新增 CI 的 URL 步骤失败。

建议：从 Astro 内容集合和同一个 postSlug 函数导出清单，直接核对产物。若保留 Python，至少使用标准 YAML 解析器，并用同一组用例验证两端契约。已有文件目前通过，并不意味着所有 schema 允许的写法都通过。

### 12. P2：历史 URL 固定清单只覆盖 5 篇文章，重定向被直接跳过

位置：`scripts/fixtures/legacy-urls.txt:5`，`scripts/verify-urls.py:179`、`:190`。

8 个 fixture 是 5 个文章地址、2 个 RSS、1 个兼容别名。其余文章 URL 从当前文件重新计算，所以修改大多数文章的 slug、日期或分类后，只要新页面生成，校验仍可能通过，旧地址消失不会被发现。`024-okr` 被特判跳过，也没有检查重定向本身及目标。

建议：保留这次迁移全部已公开文章的固定地址清单，允许新增但不默默删旧地址；将每项定义为页面或重定向，并校验目标存在。当前 61 个构建路径检查有效，但不能把它解释为全量历史链接保障。

### 13. P2：仅用 .env.production 改主域名时，SEO 产物出现两套域名

位置：`astro.config.mjs:40`、`src/lib/seo.ts:4`、`src/pages/feed.xml.ts:19`、`src/pages/posts.xml.ts:20`。

独立临时副本只在 `.env.production` 设置 `PUBLIC_SITE_URL=https://env-review.example`，并确保进程环境没有同名变量后，真实 Astro 构建成功，产物如下：

| 产物 | 主机 |
| --- | --- |
| 页面 canonical、og:url、默认 og:image、robots 的 Sitemap | `env-review.example` |
| sitemap-index、sitemap 页面 loc、两份 RSS 的频道和文章链接 | `www.weichao.ren` |

原因是配置阶段从 process.env 取值，而页面从 Vite 注入的 import.meta.env 取值，读取 `.env.production` 的时机不同。RSS 又优先使用已经带默认域名的 context.site。

建议：在配置中正确加载对应模式的环境文件，并让 SEO、RSS、robots 共享同一个最终站点地址。默认 www 配置和由操作系统环境传入变量的部署方式不受这一特定问题影响。

## UI、审美与信息组织

以下是设计判断，与上面的可复现缺陷分开记录。

整体更适合作为中文个人作品站：中文导航统一，身份更清楚，精选作品收敛到三个，项目行补上用途，Now 最新条目置顶，About 的长反思折叠后更利于扫描。下一轮视觉投入应集中在作品证据与排版细节。

| 区域 | 仍可优化之处 | 建议方向 |
| --- | --- | --- |
| 首页主标题 | 桌面“工具”在最后断成“工 / 具。”，留下短尾行 | 调整句长、容器或中文断句，让语义短语自然成行；分别看真实桌面和手机效果 |
| 作品图片 | 约 160×100 的截图仍看不清产品；二维码适合进入产品，却难以说明产品是什么 | 重要作品提供可辨认截图或单独案例页；二维码作为访问方式保留 |
| 作品说服力 | 项目已经有用途说明，但缺少完整的问题、方案、结果和本人贡献 | 先为 2–3 个代表作品写短案例，数字和上线状态只用可验证事实 |
| 首页对齐 | Hero 与后续章节的内容起点和宽度仍略不同 | 统一主要对齐线，保留必要的阅读宽度差别 |
| 文章列表 | 摘要改善了可扫读性，但日期仍占两个位置，61 篇长列表较长 | 次要日期进一步收敛，可提供“精选”入口；无需为这个规模引入搜索服务 |
| 项目页 | 上线/在研与下方分类会重复出现同一项目 | 如果两种组织方式确有作用，保持清晰分工；否则减少重复滚动 |
| 个人辨识度 | 文字是真实的，作品图仍偏缩略目录感 | 可用真实产品细节、带时间的经历和有内容的照片建立记忆点，无需新增复杂装饰动画 |
| 320px 聊天 | 发送按钮声明 40px，但 flex 挤压后约 24px 宽 | input 设置 min-width:0，按钮禁止收缩，验证可点击尺寸与软键盘场景 |

当前字体与留白不需要整体推倒重做。更高收益的顺序是：先让作品看得清、说得准，再处理孤字、对齐和重复信息。

## 性能、可靠性和底层维护

- 图片压缩已经带来实际收益：Home NAS 90,494 bytes，AquaSight 25,057 bytes，节拍器 25,598 bytes。后续按展示尺寸提供 srcset/WebP 可继续优化，但优先保留作品可辨认性。
- 渲染扫描中 19 张正文图片有 18 张懒加载；没有成对 width/height。建议补尺寸或稳定的 aspect-ratio，降低加载时布局变化。`2019-11-01-Gen10-NAS.md:69` 的原始 HTML img 没经过这次 Markdown 图片处理，仍缺相应属性和 alt。
- OG 字体请求加了超时，改善了无限等待；但所有字体都失败时 `src/pages/og/[...slug].png.ts:95` 仍抛错，没有转为默认 PNG。保留本地必要字体或图片兜底会更稳。本轮未模拟字体 CDN 故障，不声称现在分享图不可用。
- 进程内 Map 限流仍只覆盖单实例，文档现在已如实说明。若开放付费模型，应按实际流量设置共享限流或预算；纯静态问答没有必要因此引入数据库。本轮未验证生产代理头或 WAF。
- 当前 CI 主要是类型、数据、纯函数及构建检查。下一批最有价值的自动化是正文滚动可见性、API 原始字节边界、连续失败后的重试、旧 URL/锚点扫描，而不是单纯增加测试数量。
- 构建仍输出 Markdown 插件配置的弃用提示、React/esbuild 选项提示，以及 `she`、`Objective-C`、`Ruby` 的 Shiki 语言提示。当前不阻断构建，适合集中处理配置迁移和代码块语言标记。
- 仍有旧开发进程出现 `_jsxDEV is not a function`。隔离目录完成构建后重新启动 dev，聊天正常且没有该异常；未将旧进程缓存现象列为持续源码故障。开发与构建检查使用独立中间产物可以减少互相影响。

## 建议的处理顺序

1. 先消除长正文隐藏条件，并用短屏长文回归。
2. 完成聊天端到端边界：原始字节限制、每次失败的重试关联、真实错误状态、输入长度和键盘连续输入。
3. 核对新增摘要、标题层级、文章锚点；补全历史 URL 清单并消除两套解析逻辑。
4. 统一环境变量加载和部署文档，整理失效的 preview 步骤与旧域名保留策略。
5. 最后做代表作品案例、可读截图、标题断行和对齐等视觉精修。
