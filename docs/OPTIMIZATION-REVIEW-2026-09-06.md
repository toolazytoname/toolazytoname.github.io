## 建议修复的四个问题

### P2：合法的长中文对话会超过请求上限，重试无法恢复

位置：`src/components/Chatbot.tsx:61`、`:76`、`:97`；服务端限制在 `src/lib/chat-request.ts:8`。

客户端仅按最近 10 条消息及每条 4000 字符裁剪，服务端按整个 JSON 的实际 UTF-8 字节限制为 32768。两者不是同一预算。

生产构建浏览器复现：依次发送三条各 4000 个“汉”的问题，前两次请求为 12159、24348 字节，返回 200；第三次为 36537 字节，返回 413。点击“重试”仍发送 36537 字节，再次 413；随后只发“苹果”，旧历史仍使请求达到 36624 字节，继续 413。单条输入合法，但这段会话无法通过当前重试操作恢复。

建议：发出请求前对实际序列化 JSON 做 UTF-8 总量预算，优先保留最新问题，按完整轮次移除最早历史，避免把错误提示当成正常模型历史。413 应触发裁剪或提供清空会话的恢复方式，不能原样重试。服务端的字节限制应继续保留。

验收：长中文、emoji、转义字符和较长助手回复混合后仍能发送；每个请求实际字节不超限；恢复不删除页面上已经成功的对话。

### P2：异步回复结束会把用户移走的焦点抢回输入框

位置：`src/components/Chatbot.tsx:236`、`:286`。

`heldFocus` 只记录发送时的焦点，完成请求时没有重新判断用户是否已经移动。用延迟响应验证：输入框回车发送后，将焦点明确移到可聚焦的 `.chat-panel__scroll`，确认它是 activeElement；放行响应后，activeElement 变成“输入消息”输入框。键盘用户正在阅读聊天记录时会被打断。

建议：输入框 busy 时已经是 readOnly，优先依靠浏览器保留焦点；确需恢复时，要检查当前焦点及面板状态，并尊重请求期间的主动移动。请求期间按 Escape 关闭面板的抽查中，焦点最终仍在 FAB，没有证据说明这个关闭流程也有问题。

验收：发送后留在输入框可以继续输入；发送后切换到聊天记录、链接或其他控件，回复完成不改变焦点。独立复现证据见 `audits/2026-09-06-current/focus.json`，它取代总扫描结果中较粗略的焦点步骤。

### P2：代码高亮的注释文字对比度不足

位置：`astro.config.mjs:84` 的 Markdown 高亮配置，以及 `src/layouts/PostLayout.astro:289` 的代码字体样式。当前高亮使用的颜色组合需要调整，单改正文文字 token 不会覆盖 span 上的内联高亮色。

抽查 `/ios/2019/08/10/source-Aspects/`，390/768/1440 下均发现同一类 color-contrast 违规，各涉及 306 个代码 span。独立抽查 `// Aspects.h` 注释：前景 `#6a737d`，背景 `#24292e`，实际字号 12.88px，对比度 3.04:1，低于普通文字所需的 4.5:1。

建议选择对比度达标的代码高亮主题或调整注释颜色，保留语法层次；以代码块的实际计算颜色验收。这里是代码阅读与可访问性问题，不只是审美偏好。普通页面的 axe 通过结论不能覆盖这类文章。

## UI、审美与信息组织

以下为建议，不是发布阻断项。当前风格克制、页面层次清楚；下一步最有价值的是让真实内容更容易看懂。

1. **去掉没有内容的文章缩略图占位。** `src/components/PostFeed.astro:44` 为无封面文章渲染灰色空方块。首页当前四条都如此，容易像未加载完成，也占用手机上的标题宽度。无图时直接采用文字列表即可。
2. **项目图优先展示可辨认的产品状态。** `src/components/FeaturedProjects.astro:34` 开始的媒体区域把完整文档页面压到小图中，细节难辨；节拍器用二维码做主图，访客不能直接看到节拍器界面。使用真实局部截图或产品操作画面，把二维码保留为进入入口。没有素材时保留朴素文字，不生成虚构产品截图。
3. **精简手机首页的重复文案。** 项目 summary 和“问题／结果／我做的”部分内容重复，首页读到文章区域需要较多滚动。首页保留一句产品用途和最有区分度的贡献，详细案例可以留在项目介绍中。调整时检查 390、768、1440 三档，保留正文可读性。
4. **搜索与分享身份保持网名。** 站点对外只用 `lazy`，不要把真名写进标题、导航或 JSON-LD。属于识别度优化，不是 canonical 失效。
5. **优先精选内容，再考虑增加装饰。** 首页最新文章停在 2024 年，现有文案对此是诚实的。可增加人工精选的常青技术文章入口，不应仅为显得活跃而改日期。当前无需新主题系统、额外动画或全站设计重做。

## 性能、底层与维护性

- **保持现有 Astro 预渲染与 React 按需加载。** 首次访问首页的资源记录中只出现约 2.5 KB 的独立入口 JS，没有提前请求 mount-chat/React。这里不包含内联脚本，也不是压缩后线上传输指标。没有证据支持为当前规模替换框架、引入数据库或远程搜索服务。
- **为旧文章图片预留尺寸。** 61 篇构建文章共发现 19 个正文 img，其中 18 个没有显式 width/height；它们已有 lazy loading。建议读取本地图片元数据补齐尺寸，减少加载时布局移动的可能；本轮没有测得线上 CLS 数值，不能把它写成已确认的性能不达标。
- **清理一篇文章的重复 ID。** `src/content/posts/2016-07-23-symbolicatecrash.md:129` 的手写 a 标签未闭合，浏览器修复后产生多个 `dSYMUUID`；`others` 也与标题 ID 重复。建议补闭合并去重，保留旧 hash。当前同页锚点存在性检查无缺失，不将重复 ID 夸大为整篇目录不可用。
- **减少校验与框架的双重解析。** `scripts/verify-urls.py` 的手写 frontmatter 解析已覆盖上轮注释案例，但长期最好使用结构化 YAML 解析或消费 Astro 导出的路径清单。这里是维护建议，没有把已修好的具体 YAML 回归重新判失败。
- **修整开发命令与构建提示。** README 已准确说明 Vercel 适配器不支持 `astro preview`，但 package.json 仍保留该 preview 命令，可以移除或提供已验证的替代入口。上轮记录的 `$RefreshSig$` 仍是独立开发体验问题，本轮生产检查没有复现该错误。Markdown/Vite 弃用提示应在升级维护时处理，不等于构建失败。
- **部署门禁要落实到发布流程。** GitHub Actions 中有安装、测试、构建和 URL 验证；Vercel buildCommand 仅运行 build。若要求“CI 不通过不发布”，应检查实际部署是否等待检查通过。仅凭仓库配置不能判断线上是否已设置门禁，本轮未访问平台设置。
- **模型启用后再核对费用防护。** 当前限流为单实例内存计数，文档也已写明；它不能代表多实例下的全局每 IP 60 次额度。启用公开付费模型时应核实平台限流与供应商预算，按实际需要选择集中式限流。当前低流量个人站不必为此预先引入一套存储架构。
